# Working on Crema

What the app is and how it's built: [README.md](README.md). This file covers how to
**run it and see it** as an agent. Most of it was learned the hard way; follow it
instead of rediscovering it.

The block at the top (Convex) and the one at the bottom (Next.js) are generated by
those tools. Leave them in place: `next dev` re-adds its block if it's removed.

## Ground rules

- **Don't run `git`.** The owner handles version control.
- **Bun only.** There is no Node on this machine: `npx` → `bunx`, `npm run` → `bun run`.
  `bun run` / `bunx` stand in for `node` when a tool's script asks for it, which is
  how `next`, `tsc`, and `eslint` run here.
- The shell is **Git Bash on Windows**. Two consequences that bite:
  - Arguments that look like `/paths` get rewritten to `C:/Program Files/Git/...`.
    Prefix commands that take URL paths with `MSYS_NO_PATHCONV=1`.
  - `timeout` doesn't reliably stop hung children. Start anything long-lived (dev
    servers, browsers) as a **background task** and stop it with TaskStop, not
    with `timeout` or by killing processes by name.
- If a package install's output looks cut off, check the package is complete
  (`du -sh node_modules/<pkg>`). One `bun add next` left a 12 MB stub instead of
  ~200 MB, which failed with `Cannot find module '../server/require-hook'`.
  Fix: `rm -rf node_modules/<pkg> && bun install`.

## 1. Backend: a local Convex deployment without an account

If `.env.local` **exists**, it points at the owner's real deployment. Don't overwrite
it; use `bunx convex dev` as configured.

If there is **no** `.env.local`, use Convex's anonymous local mode (no login needed):

```sh
CONVEX_AGENT_MODE=anonymous bunx convex dev --once         # push functions + typecheck; writes .env.local
CONVEX_AGENT_MODE=anonymous bunx convex run seed:catalog   # sample data (no-op if beans exist)
```

- Every Convex CLI command needs `CONVEX_AGENT_MODE=anonymous` in this mode.
- It writes `NEXT_PUBLIC_CONVEX_URL` (Convex detects Next.js), which the app reads.
- The local deployment's data **persists between sessions**: expect test users and
  reviews left over from earlier runs.
- Only one local backend can run. If `convex dev --once` says "A local backend is
  still running on port 3210", a background `convex dev` is already up, and it
  pushes your changes on save. Check its log instead.
- When you're done, **delete the `.env.local` you created**, so the owner's first
  `bun run dev` sets up their own project.

Inspect data while working:

```sh
CONVEX_AGENT_MODE=anonymous bunx convex data users --limit 5
CONVEX_AGENT_MODE=anonymous bunx convex run beans:popular '{"limit":2}'
```

## 2. Run the app

Run Convex and the web server as **two separate background tasks**, each logging to a file:

```sh
CONVEX_AGENT_MODE=anonymous bunx convex dev > <scratchpad>/convex.log 2>&1   # background
bun run build && bun run start > <scratchpad>/next.log 2>&1                   # background; production, port 3000
# or, while iterating:  bunx next dev > <scratchpad>/next.log 2>&1
```

Don't use `bun run dev` (`convex dev --start "next dev"`) as an agent: it hides the web
server's output.

**Prefer the production build for checking pages.** It hydrates in seconds. `next dev`
works, but it compiles routes on first request (the first `GET /` took **44 s**), and
headless Edge then needs **15–30 s** to hydrate a page.

Wait for the server with a poll loop (`-m 60`, since the first dev request is slow):

```sh
for i in $(seq 1 90); do [ "$(curl -s -o /dev/null -w '%{http_code}' -m 60 http://localhost:3000/)" = 200 ] && break; sleep 1; done
```

`curl` is useful on its own, because every page is server-rendered:
- Missing beans, users, lists, and reviews return **404**. Protected pages return
  **307** to `/signin?redirect=…` (see `src/proxy.ts`).
- Page content, including the first page of every list, is in the HTML.

## 3. See the frontend: `scripts/shoot.ts`

```sh
MSYS_NO_PATHCONV=1 bun scripts/shoot.ts home=/ bean=/beans/<id> phone=/beans@390
MSYS_NO_PATHCONV=1 bun scripts/shoot.ts --eval "document.querySelector('header').textContent" home=/
```

For each `name=/path[@width]` it prints the PNG path (open it with the Read tool),
whether the page hydrated, and every console error or uncaught exception. `--eval` runs
an expression after hydration and prints the result. Options: `--port`, `--out`, `--wait`.

The script starts its own headless Edge with a fresh profile on a random free
DevTools port, so it never touches another browser and always starts **signed out**.
It drives Edge over the DevTools protocol with Bun's WebSocket, and closes the browser
when it finishes.

- "Hydrated" means every link, button, form, and input in `<main>` is hydrated, not
  just the header. Under Next.js, client components hydrate as their code arrives: the
  header can be interactive while a form below it isn't yet.
- On a 404 page you'll see `Failed to load resource: … 404`. That's the page's own
  status, not a broken asset.

What **doesn't** work here, so don't spend time on it:

| Tried | Result |
| --- | --- |
| Playwright `chromium.launch({ channel: 'msedge' })` under Bun | hangs |
| Playwright `connectOverCDP` under Bun | times out on the WebSocket |
| `msedge --headless --screenshot=…` | hangs, or hands off to the user's open Edge and writes nothing |
| Reusing a fixed DevTools port | if another headless Edge holds it, you silently drive *that* browser, with its cookies |
| Killing `msedge*.exe` by name | don't: `msedgewebview2.exe` belongs to the user's other apps (VS Code, etc.) |

## 4. Signed-in flows in a headless browser

Sign-in is **Google only** (Convex Auth's `google` method), and the session lives in
**httpOnly cookies** set by the `/auth/*` route handlers. A headless browser can't
sign in to Google, so the full sign-in flow can't be automated here. Leave the
in-browser sign-in check to the owner, and don't report it as tested.

What you can check:

- The backend: `convex/users.test.ts` covers account creation (username from the
  Google name, collisions, renaming) through `internal.users.createUser`.
- The sign-in page: `bun scripts/shoot.ts signin=/signin` should show an enabled
  **Continue with Google** button and no console errors. Clicking it calls
  `startSignInWithGoogle`, which needs `AUTH_GOOGLE_CLIENT_ID` set and the page's
  origin listed in `SITE_ORIGIN` (default `http://localhost:3000`).
- In anonymous local mode (§1) the backend won't deploy until `AUTH_GOOGLE_CLIENT_ID`
  and `AUTH_GOOGLE_CLIENT_SECRET` are set on it. Placeholder values are enough for
  everything except actually signing in:
  `CONVEX_AGENT_MODE=anonymous bunx convex env set AUTH_GOOGLE_CLIENT_ID placeholder`
  (and the same for the secret), then push again. This sequence hasn't been tried yet.

Still useful when driving signed-in pages some other way:

- **Wait until the page is hydrated** (elements have `__react…` keys) before clicking.
  The sign-in button is disabled until hydration.
- Navigations break an in-page `await` ("Inspected target navigated or closed").
  Act in one `Runtime.evaluate`, then poll from outside with short evaluates until
  `location.pathname` changes. New accounts land on `/settings?welcome=1`; existing
  ones go to the `redirect` target or `/`.
- Typing into React inputs: use the native value setter, then dispatch `input`:
  `Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, 'value').set.call(el, v); el.dispatchEvent(new Event('input', { bubbles: true }))`.
- Check text with **`textContent`, not `innerText`**: `innerText` applies CSS
  `uppercase`, so the "Your brews" heading reads "YOUR BREWS".
- Scope clicks to the dialog: the page behind a `<dialog>` has buttons with the same
  labels ("Like").
- To prove server rendering while signed in, fetch the page from inside the browser
  (`await (await fetch(location.href)).text()`; the cookie is sent) and look for
  `aria-label="Account menu"` in the raw HTML.
- Confirm results in the database (`convex data logs`), not only in the UI.

## 5. Checks before you hand work back

```sh
bun run typecheck                                    # strict tsc over app + convex
bun run lint                                         # ESLint (Next + Convex rules)
bun run test                                         # Convex tests via `bun test`
CONVEX_AGENT_MODE=anonymous bunx convex dev --once   # Convex's own typecheck + push
bun run build                                        # next build (also typechecks)
```

- Tests use **`bun test`**, not Vitest: Vitest 5 crashes under Bun here, on both the
  forks and threads pools. `convex/aggregates.test.ts` builds convex-test's module map
  with `Bun.Glob` instead of `import.meta.glob`.
- Next.js pitfalls hit in this codebase:
  - A Server Component that imports a **value** (not a type or component) from a
    `'use client'` file gets a client reference instead of the value. Shared
    constants live in plain modules (e.g. `src/lib/pageSizes.ts`).
  - A `<Suspense>` around the root layout's content makes Next stream early and
    commit a **200** before pages call `notFound()`. Missing pages then return 200
    instead of 404. Don't add one there.

## 6. Clean up

Stop every background task you started (Convex, Next, browsers). Delete the
`.env.local` you created in anonymous mode. Leave the user's own processes alone.
